# Dedicated security review and per-alert decision

Date: 7 November 2026. This is an independent AI-assisted security-review role within the engineering team, not an external professional certification or a penetration-test attestation. The reviewer inspected source and exact SARIF flows rather than accepting raw severity labels or the earlier proposed dispositions without examination.

## Decision

The **reported injection classifications for alerts 1–78 are approved individually for dismissal under the contracts below**: 49 test-only reported flows (`used in tests`) and 29 flows with no untrusted-input security boundary in this application (`false positive`). No query, language, test directory or entire warning class should be disabled. Each GitHub disposition must retain its individual evidence and remain reopenable. New alert IDs or changed source/trust boundaries are not preapproved merely because they share a file or query.

**This is not approval to ignore other defects or publish a validated production release.** A real cleanup retry/privacy defect was found independently of the path-injection labels. The Windows repair is reviewed and its synthetic permission-denial regression passed 87 core assertions; the complete Windows Release cross-build passed with zero warnings/errors. The analogous Mac stat-denial and rollback repairs are independently reviewed: all 18 standalone core pass groups completed, including genuine missing-file idempotence. Final platform CI must still pass after the repairs; local cross-compilation does not establish Windows native execution of new cases. No confirmed critical/high injection, arbitrary-object RCE, or cross-user compromise was established in these 78 reported flows.

The query's high/critical severity remains in the table as scanner metadata. Actual severity for these specific injection candidates is **not established as a vulnerability under the reviewed trust contract**. The separate genuine cleanup issue is graded P2 privacy/correctness; the WPF allocation race is a P3 robustness follow-up on current evidence.

- Read the source locations of every reported flow and relevant current sink/guard implementation. The baseline scan is commit `4904f2e`; fresh alerts 65–78 are commit `af60f5e`. Production/test logic was compared with current source and the focused Windows cleanup repair.

## Trust contract and limits

The application runs as the ordinary current user. Production does not accept its store root from clipboard contents, a remote request or an untrusted imported database. The public `ClipStore` constructor's directory is a trusted caller capability; `Path.GetFullPath` is not treated as authorization or a sanitizer for hostile roots. Private storage and screenshot parents are not guaranteed safe against a malicious process already controlling the same account or an administrator. Do not reuse these approvals if a future service runs elevated, accepts remote paths, imports untrusted databases or changes the caller contracts.

Windows app-owned image names use generated UUIDs; exact-parent and UUID ownership checks constrain deletion. Current screenshot validation rejects network/unsafe reparse paths and validates stable file/directory identities. Those checks reduce concrete redirect risks, but do not prove universal filesystem TOCTOU immunity. Local root/ancestor attributes queried as part of validation are intended operations, not evidence of arbitrary content-controlled output paths.

Release builders must trust the checkout, compiler, SDK, environment, PATH and runner. Choosing `DOTNET_COMMAND` or `NSIS_COMPILER` is deliberately choosing code to execute at the operator's existing privilege. Argument lists avoid shell interpretation and runtime choices are allowlisted, but a malicious selected executable can still run code. Current CI does not map clipboard, PR title/body or other external text into those executable choices. Unsigned CI artifacts from an arbitrary PR are not official binaries; verify the trusted repository and protected-main run, or use a future signed/attested release.

Test-only classifications assume a normal trusted local test harness. Synthetic GUID subdirectories and fixed fixture children are not authorization for operating on arbitrary user data, and do not promise protection from an already same-user filesystem attacker. The one fixture SQL interpolation is limited to IDs generated in that run's private synthetic database; if that helper is ever exposed to imported or external IDs, it must be parameterized/re-reviewed.

## Real findings outside the raw injection labels

1. **P2 — cleanup preflight can hide deletion failure.** `File.Exists` returns false on access/stat errors. The old Windows temporary cleanup could consequently lose the only retry reference; an existing partial image survived a chmod-000 fixture and purge incorrectly succeeded. The reviewed repair tries deletion directly and keeps failed owned paths queued; it preserves the original write error and passes the reported 87-assertion regression run. Mac baseline fixtures independently reproduced the same lost retry and two rollback orphan cases. The reviewed Mac repair directly attempts owned removal, ignores only Cocoa no-such-file, and queues known add-image/copy rollback URLs before best-effort cleanup while preserving the original insertion error. Fixed fixture outcomes were add-image asset count 0→1→0 and copy count 1→2→1; source assets remain intact. All 18 standalone core pass groups completed, including missing-file idempotence. Final integrated/native CI remains a merge/release condition. A separate path-injection dismissal must not be presented as proof this privacy behavior was correct.
2. **P3 — WPF allocation preflight/retrieval race.** Native size checking and later WPF retrieval are separate clipboard operations. Replacement between them can cause a different transient allocation before sequence checks discard the capture. No memory-exhaustion exploit, cross-user boundary break or arbitrary-object RCE was demonstrated. Atomic native capture requires synthetic Windows tests for delayed rendering, HGLOBAL/bitmap lifetime and privacy-format interoperability. It is not justified to rush new handle ownership code solely to remove a warning.
3. **P3 current / prerequisite for official distribution — artifact identity.** A successful PR build executes proposed code and is not an official release. Protected-main-only distributable upload is a useful default, not an absolute platform isolation mechanism: a malicious PR can propose its own workflow or use artifact APIs. Verify actual repository/ref/event and use signing/attestation for stronger publisher assurance.

The .NET 10 source does not restore unsafe BinaryFormatter compatibility. Current WPF uses restricted built-in handling; unsupported fallbacks throw by default. This supports the absence of a confirmed arbitrary-object RCE path in this review, not an assertion that all deserialization or image-codec risk is absent.

## Sources used to resolve API behavior

- [Microsoft File.Exists](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.exists?view=net-10.0): access/error conditions can produce false rather than an exception.
- [Microsoft File.Delete](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.delete?view=net-10.0): deletion errors must be handled; missing files do not require an existence preflight.
- [Microsoft OpenClipboard](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-openclipboard): exclusion of other clipboard writers applies while it remains open.
- [Microsoft WPF BinaryFormatter migration](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-migration-guide/wpf-applications): restricted supported types and unsupported fallback behavior.
